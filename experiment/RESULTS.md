# Experiment results (2026-10-15)

Question: can a model write correct programs in ail, a language created today that appears in
no training data, as reliably as in Rust and TypeScript?

## Setup

- 16 console tasks (stdin to stdout) with hidden tests generated by Python reference solutions.
  10 were seen by a pilot agent while the spec was being tuned; 6 are held out
  (`toposort lru intervals roman anagrams minesweeper`), written after the last spec change.
- Each (language, task) pair is one fresh agent. It reads the task and, for ail, the full
  `SPEC.md`, then writes the program once. No compiling, no testing, no second look.
- Graded by `grade.py`: compile, run every hidden test, compare stdout exactly.
- The hidden tests and their generators (`make_tasks.py`, `heldout_tasks.py`, `r3_tasks.py`) are
  not in the public repository, so the tasks remain a held-out evaluation.
- Repair round: failing pairs get the compiler output or the first failing test, once.
- Rust: `rustc -O`. TypeScript: `tsc --strict --lib es2022`, run on Node 25.

## Results: first attempt

| model | language | compiles | correct | tests passed | correct after 1 repair |
|---|---|---|---|---|---|
| Sonnet | ail | 16/16 | 15/16 | 95.8% | 16/16 |
| Sonnet | Rust | 16/16 | 16/16 | 100% | 16/16 |
| Sonnet | TypeScript | 16/16 | 16/16 | 100% | 16/16 |
| Haiku | ail v0.1.0 | 13/16 | 13/16 | 83.3% | 15/16 |
| Haiku | ail v0.1.1 | 15/16 | 15/16 | 95.8% | 16/16 |
| Haiku | Rust | 16/16 | 16/16 | 100% | 16/16 |
| Haiku | TypeScript | 16/16 | 16/16 | 100% | 16/16 |

"ail v0.1.1" is the same 16 Haiku programs, unchanged, graded by the compiler that infers
closing parentheses from indentation (see below). The only remaining failure called a helper
function the model never defined; one repair round fixed it.

Code size over the 16 Sonnet solutions: ail 24.9 KB, Rust 32.9 KB, TypeScript 21.9 KB.

## What we learned

1. **The cold-start risk did not materialize at this scale.** With nothing but a ~4,000-word
   spec in context, a model writes ail that compiles on the first attempt as often as Rust and
   TypeScript. Every Sonnet program compiled; the one wrong answer was a logic slip the agent
   itself pointed out (joining with `""` instead of `" "`).
2. **The s-expression weak spot is paren counting, not semantics.** 2 of Haiku's 3 failures
   were one missing or one extra `)`. Models indent correctly far more reliably than they count,
   so ail now treats indentation as a second witness: when the parens do not compile and the
   indentation-implied structure does, the compiler uses it (warning W0004) and `ail fix`
   writes it back. A program that compiles never changes meaning.
3. **These tasks are too easy to separate the languages.** All three are at or near 100% for
   both models. Measuring the advantages ail is designed for (no aliasing bugs, no silent
   overflow, no unhandled effects) needs harder tasks: mutation-heavy simulations where Rust's
   borrow checker bites, arithmetic above 2^53 where JavaScript numbers silently lose precision,
   and larger programs. That is run r3.
4. **Fairness bugs in the harness were found and fixed**: tsc included the DOM library, so a
   variable named `top` collided with `window.top`; with `--lib es2022` that program passes.

## Run r3: harder tasks (2026-10-16, ail 0.4 dev)

Eight new tasks (`tasks_r3/`, generated by `r3_tasks.py`) built to stress what r1/r2 did not: a limit
order book (mutation-heavy state), shortest paths with road lengths up to 10^15 (sums past 2^53, where
JavaScript numbers silently lose precision), an interpreter for a small language that must detect
64-bit overflow, an unbounded Game of Life, a preemptive CPU scheduler, JSON queries (Rust: no serde,
parser by hand), full text justification and 64-bit FNV-1a hashing. Same protocol: one fresh agent per
pair, the task and (for ail) `SPEC.md`, one write, no compiling or testing.

| model | language | compiles | correct on first attempt | same programs, fixed ail compiler |
|---|---|---|---|---|
| Sonnet | ail | 7/8 | 7/8 | 8/8 |
| Sonnet | Rust | 8/8 | 8/8 | 8/8 |
| Sonnet | TypeScript | 8/8 | 8/8 | 8/8 |
| Haiku | ail | 7/8 | 7/8 | 8/8 |
| Haiku | Rust | 8/8 | 8/8 | 8/8 |
| Haiku | TypeScript | 8/8 | 7/8 | 7/8 |

What happened:

1. **Both ail failures were compiler bugs, not model mistakes.** The SPEC says the branches of an `if`
   in statement position may have different types. The checker did not treat the last statement of a
   `while`/`for` body (Sonnet) or of a `match` arm in statement position (Haiku) as a statement, so
   `(if found (remove-at (mut book) i) (set ...))` was rejected. Fixed; the unchanged programs then pass
   every test. Writing the language with the agents keeps finding the spots where the compiler is
   stricter than the spec.
2. **TypeScript failed the interpreter task with Haiku** in a way the other two languages cannot:
   it rejected an out-of-range literal while parsing, before running the statements above it, so the
   program printed the error instead of the earlier output. (Its other "failures" in that task only
   exited with code 1 after printing the right error; the task did not specify an exit code, so those
   are counted as correct above.)
3. **The 64-bit traps did not catch the models this time.** Every TypeScript solution used `BigInt` for
   road lengths and hashes, and every Rust solution used `checked_*`/`wrapping_*` where needed. ail
   gained `checked-add/sub/mul` and `wrapping-add/sub/mul` for this run, and the models used them
   correctly from the spec alone.
4. **Models used the new features unprompted**: lambdas with `filter`/`find-index`/`sort-by`, `fold`,
   records with `with`, and string views are invisible but free.

Code size (Sonnet, all 8 tasks): see `runs/r3/`.

## Run r4: speed of the code the models write (2026-10-17)

The question changes here. r2 and r3 asked whether a model writes correct ail. r4 asks whether the
ail a model writes runs as fast as the Rust the same model writes.

Seven compute-heavy tasks: heat diffusion, segmented prime counting, integer k-means, path counting
in a grid, Collatz chains, modular matrix product, and word bigrams. Each task has hidden tests with
the usual traps (64-bit sums, floor division of negatives, ties, overflow in modular arithmetic).
Each also has one large input at the stated limits (7 to 44 MB), which is timed. The statement
says the machine has 12 cores and that threads may be used. Opus and Sonnet each wrote all
3 x 7 programs once, with no compiling and no testing.

**Correctness: 42 of 42.** Every program in every language passed every hidden test on the first
attempt. Correctness does not separate the languages on these tasks; speed does.

**Speed:** ail time divided by the time of the Rust program the same model wrote for the same task,
best of 3 interleaved runs. The programs are unchanged between the columns; only the ail compiler
differs.

| model | task | ail compiler before | after this round |
|---|---|---|---|
| Opus | bigrams | 0.51 | 0.47 |
| Opus | collatz | 1.11 | 1.18 |
| Opus | heat | 2.90 | 1.25 |
| Opus | kmeans | 1.20 | 1.06 |
| Opus | matmul | 2.13 | 1.79 |
| Opus | paths | 1.54 | 1.41 |
| Opus | primes | 1.32 | 1.30 |
| Sonnet | bigrams | 1.10 | 1.19 |
| Sonnet | collatz | 1.59 | 1.47 |
| Sonnet | heat | 3.69 | 1.82 |
| Sonnet | kmeans | 1.54 | 1.49 |
| Sonnet | matmul | 2.37 | 1.96 |
| Sonnet | paths | 1.17 | 1.09 |
| Sonnet | primes | 1.93 | 2.30 |
| | **geometric mean** | **1.55** | **1.33** |

Most runs take 0.1 to 1 s, so a few hundredths of a second of noise moves the small ratios.

What the run showed:

1. **The models write fast Rust when told about the cores.** Opus parallelized 4 of 7 Rust programs
   with `std::thread::scope`, and used flat arrays, slices without bounds checks and byte-level
   input parsing. So the Rust baseline here is far from naive.
2. **Safe parallelism gets used more.** Opus used `par-map` in 6 of 7 ail programs, against threads
   in 4 of 7 Rust ones. Sonnet used parallelism in 4 of 7 in both languages.
3. **Where the ail time went, and what changed in the compiler:**
   - Reading the input took 60% of the time in matmul and kmeans. `(for line (lines text) ...)` now
     walks the text without copying each line. `(for tok (split (trim line) " ") ...)` now
     streams when the source is any expression whose variables the loop does not change, not only a
     plain variable.
   - `par-map` started a new set of threads on every call (300 times in heat). It now runs on a
     pool started once, and each result is written straight into its slot.
   - An innermost `(for j (range a b) ...)` whose `(at v j+c)` reads stay on a Vec the loop does not
     change is tested once before the loop. If every index is in range, the loop runs without bounds
     checks; otherwise the checked loop runs and traps exactly where it would have.
   - A loop that pushes to a vector on every iteration reserves the room up front.
   - Blocks of 1 KB to 1 MB now come from ail's own allocator (power-of-two classes, shared free
     lists). On Windows the system heap serializes threads on blocks above 16 KB.
4. **What remains is mostly algorithmic or arithmetic.** In primes, Sonnet's Rust uses 256 KB
   segments that fit in cache; its ail uses 2 MB ones. In matmul, Rust sums `u64` products with
   unchecked arithmetic that LLVM vectorizes; ail checks every `*` and `+`, and the model wrote the
   inner loop as a `while`.

## Run r5: the code models write when nobody mentions cores (2026-10-17)

r4 told the models that the machine has 12 cores, and they answered with threads in Rust and
`par-map` in ail. r5 asks what they write without that hint: the same seven tasks and hidden tests,
with the performance note reduced to "the program is timed on one input at the limits stated
here". Opus and Sonnet wrote each task once in ail and Rust, with no compiling and no testing.

**Correctness: 27 of 28.** Every Rust program and 13 of 14 ail programs passed every hidden test.
The miss: Sonnet named a variable `as`, which is an ail keyword, so the program did not compile.

**What they wrote:** no Rust program uses threads. Two ail programs (Opus's matmul and primes)
use `par-map`; the rest are plain loops.

**Speed:** ail time divided by the Rust time of the same model and task, best of 3 interleaved
runs. Same programs in both columns; only the ail compiler changes. The second column is the
compiler that parallelizes independent `for` loops on its own (see DESIGN.md, "Loops that
parallelize themselves"), splits loop ranges into checked edges and an unchecked middle, and
defers overflow checks in innermost loops that only compute.

| model | task | before | automatic parallel loops |
|---|---|---|---|
| Opus | bigrams | 1.25 | 0.98 |
| Opus | collatz | 1.42 | 1.54 |
| Opus | heat | 5.04 | 1.33 |
| Opus | kmeans | 1.47 | 0.38 |
| Opus | matmul | 0.65 | 0.57 |
| Opus | paths | 1.42 | 1.28 |
| Opus | primes | 0.23 | 0.26 |
| Sonnet | bigrams | 1.46 | 1.41 |
| Sonnet | heat | 5.25 | 1.30 |
| Sonnet | kmeans | 1.31 | 0.42 |
| Sonnet | matmul | 2.02 | 0.58 |
| Sonnet | paths | 1.25 | 1.85 |
| Sonnet | primes | 0.84 | 0.52 |
| | **geometric mean** | **1.37** | **0.81** |

The machine was busier during the second column, so absolute times rose for both languages; the
ratios are interleaved and hold. Runs of 0.1 to 0.3 s (paths, collatz) move by a few tenths.

What the run showed:

1. **Without the hint, the Rust is sequential, and so is most of the ail.** That is where
   automatic parallelism pays: kmeans (a histogram and a running minimum per point) and Sonnet's
   matmul (a scratch row reused across iterations) now run on every core without a change to the
   source, and are 1.7 to 2.6 times faster than the Rust.
2. **The losses that remain are sequential by nature.** paths is a dynamic program where each cell
   needs its left neighbor; collatz fills a table where each entry needs a smaller one; bigrams
   builds a hash map word by word. Here ail is 1 to 1.9 times slower than Rust: checked
   arithmetic, 64-bit values where the Rust uses `u32`, and per-line strings.
3. **heat is limited by memory, not arithmetic.** The Rust stores the grid as `u32` and reads half
   the bytes ail's `I64` grid needs. Parallel rows cut ail from 5 times slower to 1.3.
4. **An explicit `par-map` keeps priority.** The first version also parallelized the loop over
   queries around Opus's `par-map` over segments, which made the inner `par-map` sequential and
   primes 3.5 times slower. Loops whose body uses `par-map` (directly or through a function) now
   stay sequential.


## Run r6: heavy tasks, and the GPU (2026-10-29)

r6 asks for eight compute-heavy tasks (floyd, knapsack, lcs, life, mandel, queens, reach,
sortgen), with the same "timed on one input at the limits stated here" note as r5 and nothing
about cores or GPUs. Opus and Sonnet wrote each task once in ail and Rust, with no compiling and
no testing.

**Correctness: 31 of 32.** Every Rust program and 15 of 16 ail programs passed every hidden test.
The miss: Sonnet's ail knapsack fails one of seven tests (its answer on the timed input is right).

**Speed:** ail time divided by the Rust time of the same model and task, best of 3 interleaved
runs, on a Ryzen 5 2600 with an RX 6600. Same programs in both columns; only the ail compiler
changes. The first column is the compiler of 2026-10-16 (`r6_perf_base.json`); the second adds
loops on the GPU (see DESIGN.md, "Loops that run on the GPU"): kernels compiled to SPIR-V and run
through Vulkan, outer loops in queued groups of launches, reads of a row from before the loop
(the in-place knapsack), narrow device copies and a fast path for checked 64-bit multiplication
(`r6_perf_gpu.json`).

| model | task | before | with the GPU |
|---|---|---|---|
| Opus | floyd | 1.75 | 0.33 |
| Opus | knapsack | 1.74 | 0.33 |
| Opus | lcs | 0.52 | 0.69 |
| Opus | life | 13.22 | 9.53 |
| Opus | mandel | 2.42 | 1.39 |
| Opus | queens | 0.98 | 1.37 |
| Opus | reach | 1.33 | 1.42 |
| Opus | sortgen | 0.91 | 0.52 |
| Sonnet | floyd | 1.24 | 0.19 |
| Sonnet | knapsack | 1.89 | 0.21 |
| Sonnet | lcs | 10.94 | 5.96 |
| Sonnet | life | 21.20 | 2.52 |
| Sonnet | mandel | 1.56 | 0.75 |
| Sonnet | queens | 1.10 | 0.99 |
| Sonnet | reach | 1.54 | 1.65 |
| Sonnet | sortgen | 1.11 | 0.72 |
| | **geometric mean** | **2.05** | **0.96** |

ail is faster than Rust in 9 of 16 programs, against 3 before. The machine is short of memory
and noisy: the Rust times themselves moved by up to 50% between the two columns (queens Opus,
3.9 s to 2.1 s), so single ratios move by a few tenths; the geometric mean holds.

What the run showed:

1. **Dense loops over vectors go to the GPU without a change to the source.** floyd, knapsack,
   mandel and Sonnet's life are 1.3 to 9 times faster than before, and floyd and knapsack 3 to 5
   times faster than the Rust. Every trap stays exact: a launch that traps is undone and the loop
   runs again on the CPU, which stops at the same line (`tools/gputraps.py`).
2. **Launch overhead, not arithmetic, was the limit for loops inside a sequential outer loop**
   (floyd's k, knapsack's items). Queuing the launches of a group of outer iterations and
   checking them together is what moved those tasks.
3. **The losses that remain are code that is sequential, or Rust that uses a better algorithm.**
   Both Rust lcs programs and Opus's Rust life are bit-parallel (64 cells per operation); the ail
   versions are the textbook dynamic program and grid. A plain Rust version of the same lcs
   dynamic program runs at the speed of the ail one, so that gap is the algorithm, not the
   compiler. reach is a graph search; queens is backtracking.

**Afterwards: a sliding window in the inner loop.** Opus's ail life walks each row keeping the
column sums of the last two columns in variables (`(set vl vm) (set vm vr)`), so the columns of a
row depended on each other and the kernel ran one row per work item: 2000 items, each reading
memory far from its neighbors. The compiler now gives each (row, column) its own item, which
computes the window again from the columns before it. Re-timed afterwards
(`r6_perf_gpu2.json`), Opus's life goes from 9.53 to 3.93 and the geometric mean is 0.92;
the other ratios move within the noise (Sonnet's Rust lcs measured 0.06 s here and 0.16 s
before).
